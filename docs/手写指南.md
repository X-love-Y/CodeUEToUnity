# 手写指南：每个文件夹、每个文件、以及怎么写

这份文档回答三件事：**每个文件夹干什么**、**里面的每个文件是什么**、**哪些文件要你自己写、怎么写**。

## 一、谁生成谁写：一张总表

| 路径 | 作用 | 谁生成 | 你要手写吗 |
| --- | --- | --- | --- |
| `config.yaml` | 工具的全局配置 | 手工 | 要 |
| `mappings/ue2unity.yaml` | 符号映射知识库 | 手工 | 要，最常改 |
| `prompts/system_unity.md` | 给模型的目标架构约定 | 手工 | 要，定风格 |
| `prompts/unit_translate.md` | 单单元提示词模板 | 手工 | 要，偶尔改 |
| `input/*.h` `input/*.cpp` | UE 源码（翻译的输入） | 手工 | 要，放你的代码 |
| `work/tasks/<单元>.files/*.cs` | agent 模式的人工翻译产物 | 手工 | 走 agent 时要 |
| `work/tasks/<单元>.notes.json` | 上面那个的手写元信息 | 手工 | 走 agent 时要 |
| `work/units.json` | scan 的结果 | 工具 | 不 |
| `work/tasks/<单元>.prompt.md` | plan 生成的任务包 | 工具 | 不 |
| `work/tasks/<单元>.meta.json` | plan 生成的元信息 | 工具 | 不 |
| `work/results/<单元>.json` | translate 归一化后的结果 | 工具 | 不 |
| `work/verify.json` | 编译诊断 | 工具 | 不 |
| `out/UnityScripts/*.cs` | 最终产物 | 工具 | 不 |
| `verify/CompileCheck.csproj` | 编译门禁工程 | 工具，每次重写 | 不 |
| `reports/migration_report.md` | 迁移报告 | 工具 | 不 |
| `migrate.py` | 工具本体 | 手工 | 想改功能时才动 |

## 二、`config.yaml`：全局配置

33 行，分四段。

```yaml
paths:                          # 所有路径都相对于工程根目录
  input: input                  # 去哪里找 UE 源码
  work: work                    # 中间产物放哪
  output: out/UnityScripts      # C# 产物放哪
  reports: reports
  mappings: mappings/ue2unity.yaml
  prompts: prompts
  unity_managed: "C:/Program Files/Unity/Hub/Editor/2021.3.45f1c1/Editor/Data/Managed/UnityEngine"

provider: agent                 # api = 直连模型;  agent = 用人工/智能体写好的结果

api:
  base_url: "https://api.deepseek.com/v1"
  model: "deepseek-chat"
  api_key_env: "DEEPSEEK_API_KEY"   # 只写变量名, 密钥走环境变量, 不落盘
  json_mode: true                   # 服务不支持 response_format 就改 false
  temperature: 0.2
  max_tokens: 8192
  timeout: 300

translate:
  max_fix_rounds: 2
  max_source_chars: 24000       # 单单元源码超过就截断

verify:
  target_framework: netstandard2.1
  unity_modules:                # 编译门禁要引用的 Unity 程序集
    - UnityEngine.CoreModule.dll
    # ...
```

### 手写要点

- **只改 `provider` 和 `api` 段** 就能切换工作模式，其余段落一般不动。
- `unity_managed` 换机器或换 Unity 版本时必须改。判断方法：该目录下要能看到 `UnityEngine.CoreModule.dll`。
- `unity_modules` 决定编译门禁能识别哪些 API。用了新模块（比如 `UnityEngine.AI`）就要把对应的 `UnityEngine.AIModule.dll` 加进来，否则会报"找不到类型"。
- **YAML 用空格缩进，绝对不能用 Tab。** 这是最常踩的坑。
- 写字符串时只要不确定，就加双引号。含冒号加空格、`#`、`>`、`|`、`{`、`[`、`&`、`*`、`!`、`%`、`@` 的值必须加引号。

### 改完一定要自检

```powershell
uv run migrate.py doctor
```

它会逐项检查路径、映射表能否解析、Unity 程序集是否齐全、dotnet 是否可用、以及 API 连通性。**在花 token 之前先跑这个。**

## 三、`mappings/ue2unity.yaml`：映射知识库（最重要的文件）

708 行，112 条条目。这是整个工具的价值所在：模型负责"理解"，这张表负责"不出错"。

### 结构

```yaml
meta:                # 纯给人看的说明, 工具不读这一段
  version: "0.1"
  source_engine: "Unreal Engine 5 (C++)"
  target_engine: "Unity 2021.3"

entries:             # 工具只读这一段的数组
  - id: t-vector                 # 唯一标识, 建议用 "分类前缀-名字" 的写法
    category: type               # 分类, 纯给人看, 工具不按它过滤
    ue: FVector                  # 匹配用的字符串
    unity: Vector3               # Unity 侧对应写法
    confidence: 1.0              # 0~1, 低于 0.8 的会进人工确认视野
    note: "UE 单位是厘米, Unity 是米"   # 语义差异说明, 这一行最值钱
```

### 自己加一条的完整步骤

1. 打开 `mappings/ue2unity.yaml`，在 `entries:` 下找位置（建议按分类集中放）。
2. 照着上面五个键补一条，**`id` 必须唯一**（重复会静默覆盖前一条）。
3. 存盘，跑 `uv run migrate.py scan`，看覆盖率有没有上升。

示例，我想支持 `TActorIterator`：

```yaml
  - id: x-actoriterator
    category: macro
    ue: TActorIterator
    unity: "FindObjectsOfType<T>()"
    confidence: 0.8
    note: "UE 按类型遍历关卡里的 Actor; Unity 用 FindObjectsOfType。注意遍历顺序不保证, 且开销随对象数上升, 不要在循环里反复调用。"
```

### 匹配机制（必须理解的三个事实）

**1. `ue` 字段是子串匹配，不是精确匹配，也不是正则。**

代码里就是一句"这个字符串是否出现在源码文本里"。所以：

- `ue: TArray` 能匹配到源码里的 `TArray<int32>`
- `ue: "UPROPERTY(EditAnywhere"` 故意带括号，就是为了只匹配带这个说明符的属性
- 但 `ue: Location` 这种短词会到处误匹配

**结论：`ue` 要写得足够独特。** 短到像 `Size`、`Speed` 这样的词一定要带上下文。

**2. 只有"本单元源码里出现过"的条目才会被送进提示词。**

`plan` 阶段会筛一遍，命中的条目才拼进任务包。这是刻意的设计：省 token，也减少干扰。

**3. 超过 70 条会被截断，按文件里的书写顺序取前 70 条。**

所以：**高频、通用的条目放在文件靠前的位置**。如果发现某个重要条目没进提示词，把它往前提。

### `note` 字段怎么写才有用

对比一下：

```yaml
    note: "FVector 对应 Vector3"      # 废话, 模型自己就知道
```

```yaml
    note: "UE 用厘米, Unity 用米. 位置和尺寸转换要乘 0.01, 速度同理."   # 这才是关键
```

好的 `note` 只写三类东西：

- **量纲或单位差异**：厘米和米、度每秒和插值系数
- **语义陷阱**：`Mathf.Epsilon` 只有 1.4e-45 而 `KINDA_SMALL_NUMBER` 是 1e-4，量级差了几十个数量级
- **没有对应物时该怎么办**：`SetMovementMode` 在 Unity 不存在，必须翻译成显式状态机

## 四、`prompts/`：决定输出质量的两个文件

### `prompts/system_unity.md`（46 行）

这个文件的内容会原样作为 **system message** 发给模型。它是"目标架构宪章"。

写有效约束的原则：**具体、可验证、带反例**。

```markdown
低效写法:
请写出高质量的 Unity 代码。

高效写法:
坐标系: UE 是 Z-up, Unity 是 Y-up. 不要直接把 UE 的 (x,y,z) 赋值给 Unity 的 (x,y,z);
涉及世界坐标转换时要在注释里说明映射关系。
```

第二种之所以有效，是因为它**明确禁止了一个具体动作**，模型没法含糊过去。

文件里"必须处理好的语义陷阱"那一节是这份提示词的精华，遇到新的坑就往里加一条。

### `prompts/unit_translate.md`（18 行）

单单元模板，用双花括号标记会被替换的位置。

**七个占位符，名字必须一字不差：**

| 占位符 | 会被替换成 |
| --- | --- |
| `{{UNIT_NAME}}` | 单元名（等于 `.h` 的文件名） |
| `{{SOURCE_FILES}}` | 源文件列表 |
| `{{DECLARED_TYPES}}` | 头文件里声明到的类型名 |
| `{{MAPPING_TABLE}}` | 本单元命中的映射条目，含 note |
| `{{UNMAPPED_SYMBOLS}}` | 映射表里没覆盖的符号 |
| `{{SOURCE_CODE}}` | 源码，已经包在 cpp 代码块里 |
| `{{FIX_SECTION}}` | 修复轮的附加内容，目前恒为空 |

**手写注意：**

- 替换就是简单的字符串查找替换，**拼错的占位符不会报错**，只会留下一行字面的占位符发给模型。
- 删掉 `{{SOURCE_CODE}}` 模型就看不到源码了。可以调整顺序、改周围措辞，但这七个要留着。
- 想加自己的占位符，得同时改 `migrate.py` 里 `cmd_plan` 的 `render(...)` 调用，把新键补进去。

## 五、`input/`：翻译的输入

### 配对规则

工具**只看 `.h` 文件**，然后按同名去找 `.cpp`：

```text
input/PlayerCharacter.h
input/PlayerCharacter.cpp    这两个配对成一个翻译单元, 单元名 = "PlayerCharacter"
```

三条硬规则：

1. **识别的是 `.h`，不是 `.hpp`。** 后缀是 `.hpp` 的文件会被完全忽略。
2. **`.h` 里必须出现 `UCLASS(` 或 `USTRUCT(` 或 `UENUM(` 或 `UINTERFACE(`**（注意要带左括号）。没有这个标记的头文件会被直接跳过，纯逻辑工具类、纯接口声明常踩这个坑。
3. **`.cpp` 可以没有。** 只放 `.h` 也能跑，只是模型少看到一半源码，翻译质量会下降。

### 单元名从哪来

**文件名（去掉扩展名）**，不是类名。所以 `input/Foo.h` 里写的类叫 `APlayerCharacter`，单元名也是 `Foo`。

### 一个 `.h` 里放了多个类型

会一起打包进同一个单元。这通常是好事：相关的类一起翻译，模型能看到完整上下文。

### 别一次放太多

先放 2 到 3 个文件验证流程通了，再放整批。真实项目里几百个文件既费钱又难排查。

想只处理其中一个：

```powershell
uv run migrate.py translate --unit PlayerCharacter
```

## 六、`work/`：中间产物，逐个说

这个目录整批都可以删，重跑会重建。

### `work/units.json`（scan 产物）

数组，每个单元一项，关键字段：

```json
{
  "name": "PlayerCharacter",
  "files": ["input\\PlayerCharacter.h", "input\\PlayerCharacter.cpp"],
  "declared_types": ["EMovementState", "APlayerCharacter"],
  "mapped_count": 38,
  "symbol_count": 11,
  "symbol_coverage": 1.0,
  "unmapped": [],
  "lines": 342
}
```

看 `unmapped` 数组，**这就是你的待办清单**：往映射表里补完这些，覆盖率就上去了。

### `work/tasks/<单元>.prompt.md`（plan 产物）

发给模型的**完整内容**。想知道模型到底看到了什么，打开这个文件就是。

调试提示词的时候改 `prompts/`，然后重跑 `plan`，再打开这个文件确认替换是否生效。

### `work/tasks/<单元>.meta.json`（plan 产物）

单元元信息：命中了哪些映射 id、有哪些未覆盖符号、源码是否被截断。用来排查"为什么模型没看到某条映射"。

### `work/tasks/<单元>.files/` 和 `<单元>.notes.json`（手工写）

agent 模式下，你或任何大模型对话产出的 C# 放这里。

```text
work/tasks/PlayerCharacter.files/PlayerCharacter.cs    直接放真实 .cs 文件
work/tasks/PlayerCharacter.notes.json                  元信息, 可选
```

**目录名必须严格是 `<单元名>.files`**，里面所有 `.cs` 都会被收走。

`notes.json` 的格式：

```json
{
  "confidence": 0.82,
  "notes": [
    { "severity": "manual", "text": "必须人工处理的事情" },
    { "severity": "warn",   "text": "有风险但能跑" },
    { "severity": "info",   "text": "补充说明" }
  ],
  "todos": ["在 Unity 编辑器里要做的步骤"],
  "unmapped": ["模型自己承认没搞定的符号"]
}
```

三个字段的作用要说清楚：

- `severity` 只有小写的 `"manual"` 会被算进报告的"待人工"列和"必须人工处理"清单，另外两档只是展示。
- `confidence` 是 0 到 1 的数字，直接显示在报告里。有无法自动确定的映射时，它就该低于 0.8。
- 这个文件整个都可以不写，那样 `confidence` 默认 0.5。

### 另一种交付方式：`<单元>.resp.json`

不想建目录的话，也可以写一个 JSON（自动翻译时 API 返回的就是这个格式）：

```json
{
  "unit": "PlayerCharacter",
  "confidence": 0.82,
  "files": [
    { "path": "PlayerCharacter.cs", "code": "using UnityEngine;\n\n..." }
  ],
  "notes": [ { "severity": "manual", "text": "..." } ],
  "todos": ["..."],
  "unmapped": ["..."]
}
```

**两种方式同时存在时，`.resp.json` 优先。**

代价是 `code` 字段要把整个文件塞进一行字符串，得手动转义换行符。所以**推荐用 `.files/` 目录那套**，编辑器里有语法高亮和报错，不用跟转义字符较劲。

### `work/results/<单元>.json`（translate 产物）

等于响应内容加上 `unit` 字段。报告就是从这些文件生成的，所以改这里可以直接影响报告。不推荐这么做，改 `.files/` 再重跑更干净。

### `work/verify.json`（verify 产物）

```json
{
  "success": false,
  "exit_code": 1,
  "errors": [
    { "file": "X.cs", "line": 10, "col": 14, "code": "CS1061", "message": "..." }
  ],
  "warnings": [],
  "raw_tail": "..."
}
```

编译失败时先看 `errors`，它是结构化的，比翻控制台输出快。

## 七、`out/UnityScripts/`：最终产物

`translate` 写进来的 C# 文件。文件名取自响应里 `path` 字段的**文件名部分**。

两个要知道的行为：

- **同名会覆盖**，改过名的旧文件**不会被自动清理**。想保持干净就自己清空这个目录再重跑。
- **子目录结构不保留**（当前实现只取文件名）。所以生成的脚本都是平铺的。

---

## 八、`verify/`：编译门禁

`CompileCheck.csproj` 每次 `verify` 都会自动重写，不用手动维护。它做两件事：

1. 引用 `config.yaml` 里 `unity_modules` 列出的 Unity 真实程序集
2. 编译 `out/UnityScripts/**/*.cs`

`verify/bin` 和 `verify/obj` 是 dotnet 的中间目录，已经进了 `.gitignore`。

**为什么不用 Unity 编辑器做验证**：Unity batchmode 需要激活许可证、启动要几十秒；直接拿 `UnityEngine.*.dll` 编译只要 1 到 2 秒，而且不用许可证。代价是它只做**语法和类型检查**，不验证运行时行为。

## 九、`reports/migration_report.md`：给人看的

五段：总览表、编译错误、必须人工处理、编辑器收尾步骤、未覆盖符号。

实战建议：**先看"必须人工处理"那一段**，那才是会让人白折腾半天的地方，比如碰撞层没配、按键对不上、轴值域差异。

## 十、`migrate.py`：想改功能时改哪里

659 行，按阶段分组。

| 想改什么 | 改哪里 |
| --- | --- |
| 支持 `.hpp` 后缀 | `find_units` 里的 `input_dir.glob("*.h")` |
| 改"什么算一个翻译单元"的识别标记 | `REFLECTION_RE` |
| 改符号提取规则 | `UE_PREFIXED_RE`、`UE_MACRO_RE`、`SYMBOL_STOPLIST` |
| 注释没被正确剥离 | `COMMENT_RE` |
| 喂给模型的映射条目数量上限 | `build_mapping_snippet` 的 `limit=70` |
| 让映射条目按相关度排序而非文件顺序 | `build_mapping_snippet` 里的排序逻辑 |
| 换 LLM 供应商 | `call_api`，只要兼容 OpenAI 协议就不用改 |
| 加第三种 provider | `cmd_translate` 里的 provider 分支 |
| 产物保留子目录结构 | `write_unit_outputs` 里的 `Path(rel).name` |
| 编译门禁加新的 Unity 模块 | 改 `config.yaml` 的 `unity_modules`，代码不用动 |
| 报告增加字段 | `cmd_report` |

### 加一个新阶段的模板

```python
def cmd_mynew(cfg: dict, args) -> int:
    step("我的新阶段")
    # 读上一阶段的产物: read_json(cfg["paths"]["work"] / "xxx.json")
    # 写自己的产物:     write_json(cfg["paths"]["work"] / "mynew.json", data)
    return 0        # 0 = 成功, 1 = 前置条件不满足(中断全流程), 2 = 失败
```

然后在 `main()` 的 handler 字典里注册，在 `cmd_all` 的元组里插入执行顺序。

## 十一、最常踩的坑（对照排查）

| 现象 | 原因 |
| --- | --- |
| `scan` 说找不到翻译单元 | `.h` 里没有 `UCLASS(` 之类的标记，或者文件后缀是 `.hpp` |
| 单元名和类名对不上 | 单元名取的是**文件名**，不是类名 |
| 改了 `prompts/` 但没生效 | 要重跑 `plan` 重新生成任务包，`translate` 只读任务包 |
| 提示词里出现字面的双花括号占位符 | 占位符名字拼错了，替换是纯字符串匹配，不会报错 |
| `mappings` 改了但覆盖率没变 | `ue` 是**子串匹配**；或者该条目排在 70 条之后被截断了 |
| 某个重要映射没进提示词 | 命中数超过 70 条被截断，把它在文件里的位置往前提 |
| 报告说"待人工 0"但明明有问题 | `severity` 拼成了大写或其他值，**必须是小写 `manual`** |
| 编译报"找不到类型 X" | 该类型所在的 Unity 模块没加进 `unity_modules` |
| `out/` 里有上一次的残留文件 | 同名会覆盖，改过名的不会自动删，手动清空再重跑 |
| YAML 解析报错 | 用了 Tab 缩进，或者含特殊字符的值没加引号 |
| 提示"环境变量 XXX 未设置" | `$env:` 只对当前终端窗口有效，换窗口要重设 |

## 十二、推荐的手写工作流

日常只有三个循环。

**循环 A：补知识（最常做）**

```powershell
uv run migrate.py scan          # 看 unmapped 清单
# 往 mappings/ue2unity.yaml 里补几条
uv run migrate.py scan          # 确认覆盖率上升
```

**循环 B：调输出质量**

```powershell
# 改 prompts/system_unity.md 里的约定
uv run migrate.py plan
# 打开 work/tasks/<单元>.prompt.md 确认改动生效
uv run migrate.py translate
uv run migrate.py verify
```

**循环 C：加新的迁移范围**

```powershell
# 把新的 .h/.cpp 放进 input/
uv run migrate.py doctor        # 确认环境没问题
uv run migrate.py all
```
